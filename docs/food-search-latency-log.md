# 음식 검색 API 지연·타임아웃 대응 기록

> 포트폴리오 "실패를 회복한 경험"용 원본 기록. 2026-09-17 기준으로 정리.
> 출처: `functions/index.js` 코드와 주석(CACHE_VERSION 변경 이력), 작업 세션 기록.

## 1. 배경

- 음식 이름 검색은 Cloud Function `searchFood`(서울 리전 `asia-northeast3`)가
  식약처 식품영양성분DB 공공데이터 API(`apis.data.go.kr`)를 호출하는 구조.
- 한 번 검색할 때 API를 여러 번 병렬로 호출함(전체 문장 + 가장 긴 토큰 등).
- 처음부터 3단 캐시를 두고 있었음: 인스턴스 메모리 → Firestore `foodSearchCache` → API.

## 2. 문제 발생 (2026-09-03, 앱스토어 출시 직후)

- **증상:** 캐시에 없는 새 검색어는 전부 "검색 결과 없음"으로 나옴.
- **원인 추적:**
  - GCF(서울) → data.go.kr 요청이 25초 타임아웃에 걸림.
  - 같은 API 키로 로컬에서 호출하면 1초 안에 정상 응답 → 키나 코드 문제가 아님.
  - data.go.kr이 클라우드 IP 대역을 스로틀링하거나 차단한다는 알려진 이슈와 증상이 일치.
  - 재배포하자 잠깐 회복됨(인스턴스/IP가 바뀐 영향으로 추정).
- **숨어 있던 2차 버그:** 타임아웃으로 실패한 결과를 "0건"으로 처리해 캐시에 저장함.
  그래서 API가 회복된 뒤에도 해당 검색어는 한동안 계속 "결과 없음"으로 나옴(캐시 오염).

## 3. 1차 대응: 빨리 실패하고 덜 호출하기 (09-03)

| 조치 | 변경 | 의도 |
|---|---|---|
| 검색 1건당 API 호출 수 줄이기 | `MAX_API_QUERIES` 4 → 2 | 동시에 몰리는 요청을 줄여 스로틀링에 덜 걸리게 |
| 타임아웃 줄이고 재시도 추가 | axios 타임아웃 25초 → 6초, 네트워크 오류 시 1회 재시도 | 사용자를 25초씩 기다리게 하지 않고, 막힌 요청은 다시 시도 |
| 실패와 0건 구분하기 | 모든 쿼리가 **오류**로 실패하면 `unavailable` 에러를 던짐 | 실패 결과를 캐시에 넣지 않음. 앱에는 "결과 없음" 대신 "식품 정보를 불러오지 못했어요 / 다시 시도" 표시 |
| 캐시 수명 늘리기 | 결과가 있는 검색은 7일 → 30일 보관, 0건은 1시간 | 식약처 데이터는 거의 안 바뀌므로 API를 부를 일 자체를 줄임 |
| 캐시 자동 정리 | Firestore TTL 정책을 `expiresAt`에 적용 | 오래 보관해도 만료된 문서는 자동으로 삭제 |

## 4. 부작용과 재조정 (09-05)

- 같은 시기에 검색 품질 기능을 넣음(원재료 "_생것" 변형 조회, 예외 표제어,
  품종 자동 나열 등, CACHE_VERSION v4~v8).
  그 결과 **검색 1건당 동시 API 호출이 최대 2개 → 최대 4개**로 다시 늘어남.
  → 품질 개선이 1차 대응 효과를 일부 되돌린 셈.
- 로그를 보니 성공한 호출도 대부분 **3.7~4초**가 걸렸음.
  6초 타임아웃과 차이가 너무 작아서 정상 요청까지 타임아웃에 걸리고 있었음.
- 시도한 것:
  - **v9:** 타임아웃 6초 → 9초로 완화. 메인 쿼리에서 이미 정확히 일치하는 결과가 나오면
    원재료 변형 조회를 건너뛰도록 **순차 실행**으로 바꿔 동시 호출 수를 줄임.
  - **v10:** 순차 실행은 **되돌리고 병렬 실행으로 복귀**. 9초 타임아웃은 유지.
    - 판단 근거: data.go.kr에서 확인할 수 있는 건 일일 트래픽 한도(10,000건)뿐이고,
      동시 요청 제한이 있는지는 알 수 없었음. 그래서 동시 호출을 줄여도 효과가 **불확실**했음.
      반면 순차 실행은 지연시간이 약 2배로 늘어나는 **확실한** 비용이었음.
      게다가 캐시 미스일 때만 API를 호출하므로 실제 부하는 대부분 캐시가 흡수함.
  - 함께 고친 버그: 폴백 토큰 조회로 결과를 건졌는데도 `unavailable`을 잘못 던지던
    경계 조건을 수정.
- 한 번 적용한 최적화를 근거를 따져 보고 되돌린 것이 이 단계의 핵심 판단.

## 5. 근본 해결 검토: 외부 API 의존 없애기 (09-07, 설계만 함)

지금까지는 모두 "불안정한 외부 API를 덜 아프게 쓰는 법"이었을 뿐, 원인은 그대로 남아 있음.
그래서 식약처 통합식품영양성분DB 전체 파일(CSV 약 4.6만 건)을 미리 받아두고
검색하는 방식을 비용과 구조 측면에서 비교함.

| 안 | 방식 | 비용 | 장단점 |
|---|---|---|---|
| 현재 | GCF → data.go.kr 실시간 호출 | 거의 0원 | 타임아웃·불안정 |
| A (추천) | Firestore에 한 번 적재 + 이름을 바이그램(n-gram) 토큰 배열로 저장해서 쿼리 | 읽기 과금, 월 수천 원대 예상 | 빠르고 안정적이지만 검색 설계가 어려워짐 |
| C | 전체 데이터를 SQLite 파일로 만들어 Cloud Storage에 올리고, 앱이 한 번 받아서 로컬 검색 | 읽기 비용 0, 다운로드 대역폭만 | 오프라인 검색 가능. 데이터 갱신·앱 용량 관리가 필요 |

- 예상 작업량: 반나절~하루.
- **현재 상태: 미구현.** 운영 중인 검색은 여전히 3~4단계의 완화책 위에서 동작함.

## 6. 지금 구조 요약 (09-17 코드 기준)

- 캐시: 메모리 → Firestore(결과 있음 30일 / 0건 1시간 / 에러는 저장 안 함, TTL 자동 삭제)
- API: 1차 2개 쿼리 + 원재료 변형 + 예외 표제어를 **병렬** 호출하고,
  결과가 0건이면 폴백 토큰 1개를 추가로 조회
- 타임아웃 9초 × 최대 2회 시도, 앱 쪽 callable 타임아웃 45초
- 앱: 입력 후 500ms 디바운스, 실패하면 "다시 시도" 버튼과 문의 버튼 표시

## 8. 배운 점 (초안)

- 로컬에서는 정상인데 클라우드에서만 실패하면 **네트워크 출발지(IP)**부터 의심한다.
- 실패를 "결과 없음"으로 삼키면 **캐시가 오염돼** 장애가 복구된 뒤에도 문제가 남는다.
  에러와 빈 결과는 반드시 구분한다.
- 타임아웃 값은 추측하지 말고 **실측 응답시간 분포**를 보고 정한다(6초는 정상 응답 4초와 너무 가까웠음).
- 최적화도 가설이다. 효과가 불확실하고 비용이 확실하면 되돌릴 줄 알아야 한다(v9 → v10).
- 기능을 추가하면(품질 개선) 기존 완화책(호출 수 제한)이 조용히 무너질 수 있다.
- 완화책을 쌓는 것과 원인을 없애는 것은 다르다. 결국 외부 의존을 제거하는 설계가 필요하다.
